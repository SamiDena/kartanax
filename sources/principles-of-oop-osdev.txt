Abstract

This paper presents three principles for the design and construction of objectoriented operating systems. These principles are based on the design of Choices, an
object-oriented operating system that is implemented on the Encore Multimax shared
memory multiprocessor. Choices is written entirely in C++, an object-oriented language that supports inheritance through class hierarchies. C++ is compiled, rather
than interpreted, so Choices executes directly on the hardware without any special
run-time support.
The rst principle is to model the hardware/system software interface by a framework of interacting components. The state of the model should re ect the state of
the hardware and manipulation of the model should modify the state of the hardware.
The second principle is to provide a uniform mechanism for application-to-system and
for application-to-application communications. In an object-oriented operating system
architecture this should be the invocation of a method on an instance of a system or
application object. The third principle is to organize an object-oriented operating system as a member of a family of operating systems. This family should be represented
as a class hierarchy that forms a taxonomy for operating system algorithms and data
structures.
We discuss these principles using examples taken from the Choices family of operating systems.

Introduction

Advances in operating system design and architecture require experiments in which theoretical proposals are evaluated by their performance in practical implementations. The outcome
of this experimentation often involves observations that can be factored into new theories.
In the spirit of experimental evaluation, we have built an object-oriented operating system
for a network of shared memory multiprocessors. The system is non-trivial in size and function. It consists of over thirty thousand lines of code and was built by four programmers.
It supports three standard le systems, provides virtual memory, distributed virtual memory, multiprocessor parallelism and synchronization, and TCP/IP over Ethernet. It has an
object-oriented application interface for parallel applications written in C++, as well as nonobject-oriented interfaces for C and FORTRAN. The purpose of this paper is to report three
principles that we have applied in our work that govern the construction and architecture of
an object-oriented operating system.
In our paper, we distinguish between an object-based and an object-oriented software
system. An object-based software system uses encapsulation to hide data representations,
and provides an interface based on operations which separates de nition and application
from implementation. Such a system may include classes [19], modules [30], or packages [23]
to de ne a set of object instances . An object-oriented software system, on the other hand,
includes a class hierarchy and uses inheritance [12], in which a class de nes a template for
its instances. Subclasses modify and augment this template. The class introduces de nitions
of methods (or operations) and instance variables which are inherited by its subclasses. The
methods may be invoked on all instances of subclasses of the class.
We also distinguish between an operating system that is constructed as an object-oriented
1
software system and one that provides services within an object-oriented architecture . The
former system has software components that are structured by class and subclass. The latter
system provides an environment that supports the dynamic de nition of class hierarchies and
inheritance for system programs and applications.
The Choices operating system [4, 5, 6, 28], built at the University of Illinois, is an objectoriented software system and provides an environment with an object-oriented architecture
for system and application programs. The construction of Choices has taken about two years

following conclusions which we propose as guiding principles for building object-oriented
operating systems:
1. A framework 2 of interacting components should be built to model the hardware/system
software interface. The state of the model should re ect the state of the hardware, and
manipulation of the model should modify the state of the hardware. In this way,

2.1

Motivations for Building New Operating Systems

Operating systems evolve to support new hardware architectures and new applications.
Evolving operating systems tend to grow and become less modular. Eventually, system developers may suspend this evolution pending a major revision of the operating system code.
For example, such a revision occurred in the UNIX operating system when the University
of California, Berkeley added paged virtual memory. Occasionally, new operating systems
are needed to introduce innovative designs. For example, Multics [9] was introduced to provide time-sharing facilities, and the V [8] system was developed to support message-based
systems.
Our motivation for building a new operating system stems from advances in both software
and hardware technology. For example:
1. Advances in hardware technology facilitate the concept of distributed virtual memory on networks of shared memory multiprocessors. Programming these machines is
more dicult than programming a single shared memory multiprocessor because of
the di erent mechanisms for communication.

2. Network hardware is improving rapidly. For example, the UltranetTM supports an 800
megabits/second transfer rate. At that speed, communications protocol processing
becomes a major bottleneck given conventional distributed operating system architectures. Gigabit/second network hardware may encourage distributed virtual memory,
xed sized messages, and many other innovations and will further increase demands
on software.
3. Embedded real-time computer systems require ecient tailorable operating systems
with predictable performance. With object-oriented software technology, custom operating systems may be tailored for embedded systems by re ning the system from a
family described by a class hierarchy.
2.2

Related Research

Organizing an operating system is a dicult task. Many di erent approaches to structuring
operating systems have evolved in response to advances in hardware technology and improvements in software engineering techniques. Operating systems have been organized by
hiding machine dependencies using a monolithic kernel [2], by providing a machine independent kernel that hides the details of sharing of a CPU among concurrent processes, by
structuring the kernel into layers of processes [11], by providing a functional hierarchy [13],
and by representing the mechanisms, services, and abstractions of an operating system as
objects [14].
Both the monolithic and kernel approaches are suitable for small operating systems, but
do not scale up well because they lack internal structure. The kernel approach helps by
separating an operating system into a set of cooperating processes communicating through
the kernel. Layering the contents of a kernel is a practical solution to structuring large
4

operating systems and has been applied to many of today's major operating systems [1, 10,
22, 26].
The major diculty with building layered operating system kernels is determining the
layer in which processes or functions belong and structuring the internals of each layer. Since
a layer may only rely on the processes or functions provided by lower layers, careful planning
is necessary. For example, in virtual memory systems, the paging mechanisms must use the
disk devices drivers. But, the memory that the disk drivers use must be coordinated with the
virtual memory management. Such circular dependencies are the most dicult problem in
designing the layers of an operating system. The capability-based approach helps to reduce
the problems caused by such cyclic dependencies since capabilities can be used to represent
arbitrary networks. However, such arbitrary networks lack structure (unless the objects are
organized into layers.)
Each approach has merits in terms of simplicity or coping with complexity. Next, we
describe how class inheritance is used as a design tool.
2.3

Class Inheritance as a Design Tool

In object-oriented design and programming, an object is the basic entity for abstraction. An
object is de ned as an instance of a class . A class de nes the interface and encapsulates an
implementation for its instances (objects). The class can be thought of as a template . The
interface de ned by a class provides the only means by which other entities in the system
can access instances of the class and perform operations upon them.
The interface de ned by a class need not always be fully speci ed. Part or all of it can be
taken from other classes. This acquisition of pieces of a class interface from other classes is
called class inheritance . The classes providing the inherited parts are usually called parent
classes. The inheriting class is usually referred to as a sub-class. Further subclassing leads
to the development of a class hierarchy in which only the upper levels need be understood
in order to infer some of the functionality of the entire system. Class inheritance also allows
speci cation of only the di erences between a new class and some existing classes.
All machine dependencies , operating system mechanisms (e.g., page table management),
operating system policies (e.g., schedulers) and design decisions are encapsulated within
classes in Choices. Design decisions are implemented as a potential set of subclasses. An
abstract class speci es a general behavior and protocol or signature (the methods that may
be used on instances of the class and its concrete subclasses). A concrete class re nes the
implementation of an abstract class. Abstract classes are used in our system design to specify
operating system abstractions. Concrete subclasses are used to specify particular versions,
policies or mechanisms that implement the abstraction.
In other papers we have discussed the use of this methodology to design process management and exception handling [28], le systems [20], and virtual memory management [6]
within Choices.

We would like to emphasize that the use of class hierarchies to structure operating
systems is orthogonal to the layering of a system. The hierarchies add structure to the
internals of a layer or kernel. An object instantiated within one layer may access objects in
other layers. Class inheritance allows references to these objects in an organized manner.
The class hierarchical approach also encourages code reuse within an operating system
layer, between operating system layers, and across systems [18, 20, 21, 28]. We will give
examples of these in later sections.

Abstract Modelling

The rst design principle we discovered from our work with Choices is that unstructured
entities should be hidden by an object-oriented framework through which they can be manipulated. In particular, this requires constructing an object-oriented model of the hardware.
The model provides an abstraction of entities such as the virtual memory dynamic address
translation tables, processor states, DMA, and physical memory. The object-oriented operating system is then implemented using the model. The model is de ned in terms of instances
of abstract classes. The abstract classes have concrete subclasses that represent speci c
hardware devices, such as a speci c brand and model of memory management unit (MMU).
This interface allows operating system algorithms and data structures to be constructed
without knowledge of the details of the speci c hardware being used. The abstract classes
act as place-holders for the concrete subclasses, instances of which are used to implement the
system. The model is a framework of interacting class instances because the manipulation
of one abstract hardware device may a ect other hardware devices. For example, turning
the MMU on will impact the addressability of other hardware devices.
3.1

Applications of Modelling in Choices

The Choices process scheduling framework is a good example of the
application of the modelling design technique. An instance of class Process encapsulates the
state of the hardware required to execute a process. Subclasses of Process include ApplicationProcess, SystemProcess, and InterruptProcess. Each re ects various specializations of
class Process. Instances of these subclasses are manipulated by schedulers using the Process
class methods.
The abstract class ProcessContainer [18, 28] provides the interface for a generic container
of Process instances. Instances of subclasses of ProcessContainer provide for the collection,

The CPU subclass of ProcessContainer models the hardware that executes Processes.
The CPU subclass is also abstract. In a multiprocessor, instances of subclasses of class CPU

Subclasses are used to implement specialized policies. For example, the implementation
of a semaphore also exploits the ProcessContainer subclasses to provide di erent policies.
The semaphore queue is represented by using an instance of a subclass of ProcessContainer.
The particular subclass of ProcessContainer chosen for this instance will a ect the behavior
of the semaphore. A FIFOProcessContainer provides a standard policy for managing the
semaphore queue, but in real-time systems a PriorityProcessContainer might be preferred.

class is all that is needed to implement the rest of a machine independent memory management system. Concrete subclasses of AddressTranslation are created to represent dynamic
address translation mechanisms for speci c hardware architectures. The instances of particular concrete subclasses of AddressTranslation allow the actual hardware to be completely
hidden.

Uniform Access

Because Choices is an object-oriented system (both internally and as an environment), uniform access implies that all services should be performed by objects invoking methods on
other objects. In Choices, method invocation can have one of two characteristics. If both
objects involved are in the same virtual address space, the method invocation is called
intra-address-space . Choices is implemented in the C++ programming language [29]. Object method invocation in regular C++ programs falls into this category. If the objects lie
in di erent address spaces, the invocation is called inter-address-space . Inter-address-space
invocations may involve two objects on the same machine or on di erent machines. The
uniform access principle requires the mechanism of object method invocation to be the same
in all three of these cases. In fact, no C++ compiler modi cations are necessary to support
inter-address-space method invocation in Choices. We believe that inter/intra-address-space
method invocation is a natural extension of the distributed systems approach of supplying
a uniform method (like ports in Accent and Mach [25, 24] or Processes in the V System
[8]) for accessing local and remote objects. To support our principle, we rst describe our
implementation of inter/intra-address-space method invocation. Then we discuss its bene ts
and application in distributed systems.
4.1

Object Method Invocation

C++ is a statically typed object-oriented language. Every object contains a pointer to a perclass table of the addresses of the entry points of the methods for its class3 . When a method
is invoked on an object, the entry point of the method is looked up in this table at run-time
using an index that is determined at compile time. The compiler implements inheritance by
copying the entries from the table of the parent class into a table for the subclass. Table
entries corresponding to methods that are rede ned by the subclass are replaced with the
addresses of the entry points of the new method de nitions. The principle of uniform access
allows a nameserver to return a reference to an object in the same address space, a proxy of
an object in another address space, or a reference to a stub object that will perform RPC's
[3] to a remote object. A method may be invoked on any of the three without requiring any
modi cation of the application code. Nameservers also support the notion of subclassing
and inheritance. A request to a nameserver includes a class de ning the the interface that
the application will use to access the instance. The actual object returned by the nameserver
may be an instance of a subclass of the requested class. Inheritance guarantees the correct
object-oriented interpretation of the invocations of superclass methods on an instance of
a subclass. This mechanism permits abstract services to be de ned by the system or by

4.2

Inter-Address-Space Method Invocations

The ObjectProxy class facilitates inter-address-space method invocation. Choices nameservers create and return instances of ObjectProxy in response to a request for an object in
another address space. The application uses the ObjectProxy instance to invoke a method on
the object in the other address space. Using the standard C++ method invocation described
above, the method call is made to the function at the location speci ed by indexing the
ObjectProxy method table. This function maps the method invocation on the target object
to the inter-address-space method via whatever communications and mapping mechanisms
that are needed. In this way, ObjectProxies act as surrogates for other objects, but this fact
is unknown to the client.
The methods of class ObjectProxy trap their invocation to a dynamic method lookup
function within the Choices kernel. This function implements the actual inter-address-space
method invocation using information provided by the nameserver (during the initial request)
and the descriptor for the target object (stored in the ObjectProxy instance).
Multiple mechanisms for providing inter-address-space method invocation are possible
under Choices. Three currently being researched are shared memory, distributed virtual
memory, and message passing. Which mechanism to use depends on performance and the
relative locations of the two objects involved.
In Choices, an object can be created in an independent virtual memory
address space and its lifetime may be independent of any one process. This allows the
creation of various forms of servers. In Choices, if an application and a server object are
resident on the same machine, the kernel lookup function adds the virtual address mappings
for the object's data and code to the application's virtual address space for the duration of
the call.
Shared Memory.

In the special case where the objects are both resident
on separate machines and both machine are of similar architecture with respect to data
representation, a distributed virtual memory mechanism can facilitate method invocation.
Two options present themselves in this case. First, the remote object can be made to
appear as if it were local to the invoking object's machine by sharing its data (and possibly
its code) over the network via paging during the method invocation. This solution works
well for small objects or for large objects that are very sparsely accessed. In the case that
the remote object is quite large, a second option is to transfer the process from its CPU
ProcessContainer on the local machine to a CPU ProcessContainer on the remote machine
(i.e., process migration).

A message passing implementation of inter-address-space
method invocation to a remote machine is more complicated than the above two cases.
Such an implementation does allow distributed systems to have very di erent processor
architectures. In a message passing implementation, the arguments must be copied between
the two machines involved. To do this properly, type information must be used to encode the
arguments to the method. We are examining the application of existing solutions like RPCs
and stubs or wrappers to this problem in Choices. Stubs are responsible for encoding the
arguments in messages to the remote machine. A stub at the other end is then responsible
for decoding the arguments and nally invoking the method on the remote object.
We feel that the uniformity of accessing objects in any address space via the same mechanism is an invaluable aid in application writing. In conventional distributed systems, objects
within an application's address space are usually accessed by dereferencing pointers to memory, while remote objects are accessed by sending a message to a remote process (or a port
which represents the remote process). Local objects within an application's address space
can be accessed by messaging, but this is usually inecient. Object method invocation, as
implemented in languages like C++, provides the uniform interface with little or no extra
cost.

Taxonomies

The principle of structuring Choices as a class hierarchy of operating systems algorithms
and data structures arose from the e ort to design a family of operating systems that could
be customized for particular hardware architectures and applications. Choices uses abstract
classes to de ne interfaces for its components; these abstract classes are specialized as concrete subclasses in order to provide a particular customization. As we proceeded to build
specializations of our operating system components, we discovered that the class hierarchy
we created represented a taxonomy4 of the algorithms and data structures that could be used
in customization of speci c members of a family. Deliberately building our class hierarchy
as a taxonomy would reduce the future e ort to adapt the family of systems to include a
new customization. The taxonomy represents a theory of the organization of a family of
operating systems that can be evaluated experimentally by building new family members.
When a new operating system concept is developed that ts into the theory, new subclasses
are added to the class hierarchy, and the taxonomy is augmented. If the new concept does
not t into the theory, the class hierarchy must be modi ed and the taxonomy revised.
The organization within a hierarchy re ects how system designers view the relationships
between classes which model similar concepts. The closer two classes are in the hierarchy,
the more related should be their corresponding concepts. When distinguishing between
major categories of abstract classes, we use signatures, i.e., the set of messages or methods
to which an object responds. Within each category, however, we arrange subclasses to
maximize design and code sharing, since closely related objects are most likely to contain

Choices

The history of the Choices le system directory classes exempli es the principle of revising a hierarchy when added classes do not t well into an existing taxonomy.
After building our le system hierarchy, we examined it to see if it was general enough to
support other stream-oriented le systems; speci cally, we tested our hypothesis by trying
to add support for MS-DOS. When we added the MS-DOS classes, our perspective changed
from a UNIX-oriented view of le systems to a more general stream-oriented view. Thus our
class hierarchy required considerable rearrangement. Nevertheless, much of the old hierarchy
was reused, including both code for the class de nitions and class declarations [20].
We originally viewed directories as subclasses of MemoryObject, an abstract data storage and retrieval object, because they are treated as special les in UNIX. The MS-DOS
directories did not t into the hierarchy. Therefore, we introduced the abstract class, ObjectDictionary, to model logical containers of objects. Concrete examples of ObjectContainer
are BSD UNIX directories, System V UNIX directories, and MS-DOS directories. Instead of
being characterized by a read/write signature, ObjectDictionaries provide the object naming methods: lookup, add, and remove. They refer to an underlying MemoryObject for the
directory's internal data. See Figure 2.
A taxonomy of operating system components, maintained as a class hierarchy, provides
both an abstract and a practical classi cation scheme. Abstract classes de ne the fundamental functions of components of an operating system. The concrete classes implement
these functions in a working member of an operating system family. Using a taxonomy of
operating system algorithms and data structures to organize the class hierarchy provides
a useful guideline to the developer, reduces any subsequent e orts to port or modify the
system, and facilitates customization.
